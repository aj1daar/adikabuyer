# Architecture

## Services

| Service | Port | Notes |
|---|---|---|
| `frontend` | 5173 | Vite dev server, talks only to the gateway |
| `api-gateway` | 8080 | Spring Cloud Gateway, routes `/api/catalog/**` and `/api/orders/**`, handles CORS |
| `catalog-service` | 8081 | Products, variants, inventory, media upload, auth |
| `order-service` | 8082 | Checkout, order persistence, Telegram notifications, publishes order events |
| `postgres-db` | 5433 (host, dev only) | Hosts both `adikabuyer` (catalog) and `adikabuyer_orders` (orders), each with its own Flyway history. Prod publishes no host port. |
| `rabbitmq` | 5672 / 15672 (dev only) | Order-placed event bus. Prod: broker port unpublished, management UI bound to `127.0.0.1`. |
| `minio` | 9000 / 9001 (dev), `127.0.0.1` only in prod | Local S3 stand-in for product media |

In dev, `postgres-db`, `rabbitmq`, and `api-gateway` run in Docker; `catalog-service`, `order-service`, and the frontend run on the host, reached via `host.docker.internal`. `docker-compose.prod.yml` containerizes everything instead.

## Order flow

`POST /api/orders/checkout` persists the order and its line items to `order-service`'s own database (`customer_order`/`order_item`), publishes an `OrderPlacedEvent` to the `order.exchange`/`order.queue` topology, and notifies every registered Telegram admin chat with the order details — in that order, with the Telegram call wrapped so a delivery failure there never fails the checkout itself. `catalog-service` consumes the same RabbitMQ queue and decrements `variant.stock_quantity`; an `IN_STOCK` variant flips to `SOLD_OUT` at zero stock (a `PRE_ORDER` variant keeps its status). `GET /api/orders` (admin-only) lists persisted orders for the admin panel's Заказы tab.

`InventoryListener.handleOrderPlaced` is idempotent: the whole method runs in one `@Transactional`, and before touching any stock it checks `processed_order_event` for the event's `orderId` — already there means it's a redelivery of an event whose deduction already committed (broker/consumer disconnect between commit and ack is the realistic trigger, not a mid-loop exception, since a mid-loop throw rolls the whole transaction back and simply retries cleanly), so it returns without re-deducting. Processing writes a `processed_order_event(order_id)` row in the same transaction as the stock updates, so both commit or neither does. `order.queue` also has a dead-letter routing (`x-dead-letter-exchange`/`x-dead-letter-routing-key`, via `app.rabbitmq.dead-letter-*`) plus `spring.rabbitmq.listener.simple.retry` (5 attempts, exponential backoff) — a message that keeps failing lands in `order.queue.dlq` after retries are exhausted instead of requeuing forever, which is what Spring AMQP does by default with no retry/DLX configured at all.

**Deploy note:** RabbitMQ queue arguments can't be changed on an already-declared durable queue — a running broker with the old, argument-less `order.queue` will refuse to redeclare it with the new dead-letter arguments (`PRECONDITION_FAILED`) and `catalog-service` will fail to start. Before deploying this change against an existing broker (prod's `rabbitmq-data` volume persists queues across deploys), delete `order.queue` by hand first (RabbitMQ management UI or `rabbitmqctl`) — it's safe to lose whatever's sitting in it since any in-flight order event just gets redelivered and reprocessed once `order-service` republishes or the broker requeues on reconnect.

`Variant.status` (`IN_STOCK`/`PRE_ORDER`/`SOLD_OUT`) is otherwise admin-set, not purely inventory-derived: `ProductForm`'s per-variant toggle sends it on create/update. Picking "Под заказ" forces `stockQuantity` to 0 and disables the stock input in the admin form — there's no way to enter a quantity for a pre-order variant, in the form or in `CatalogService` (which re-zeroes it server-side regardless of what the request says). "Солдаут" keeps whatever stock number it had, so un-archiving restores it. Quantity is only editable while a variant is "В наличии". The zero-stock auto-flip from the order-placed listener only ever pushes an `IN_STOCK` variant *into* `SOLD_OUT`, never back out — switching back to `IN_STOCK` and setting a real stock number is a manual admin action. A `SOLD_OUT` variant is hidden from the storefront (attribute selectors, catalog card); when every variant of a product is `SOLD_OUT` the product is archived — dropped from `GET /api/catalog/products`, `/categories`, and `/products/{id}` (404) — while the admin dashboard fetches with `?includeArchived=true` and flags it "В архиве".

Telegram admin registration: `order-service` long-polls `getUpdates` on a daemon thread (no public webhook needed) — set `TELEGRAM_BOT_TOKEN`/`TELEGRAM_REGISTRATION_PASSWORD` and message the bot the password to have that chat's id stored in `telegram_admin` and start receiving order notifications. Sending `/stop` removes the chat from `telegram_admin`. Without a token configured the poller and notifier no-op. Only run one instance of `order-service` against a given bot token at a time — two pollers race for the same `getUpdates` response, and whichever wins registers the admin in *its own* database, not necessarily the one you meant to update. Who's subscribed is visible in `AdminDashboard`'s Telegram tab (`GET /api/orders/telegram-admins`, admin-only via the same `/api/orders/**` security rule as the rest of the controller) — view-only, since unsubscribing is already self-service via `/stop`.

`DELETE /api/orders/{id}` (admin-only) hard-deletes an order and its items (cascade).

The cart groups items into "В наличии"/"Под заказ" sections whenever both are present, and lets the customer pick "Вместе" (one delivery, once everything's ready) or "Раздельно" (two deliveries — in-stock items ship first, pre-order items separately). "Раздельно" submits two independent `POST /api/orders/checkout` calls (one per group) rather than a single split order server-side, so it doubles the delivery fee and produces two rows in the admin orders list; there's no cross-order linkage, and a failure partway through (one call succeeds, the other doesn't) isn't rolled back.

## Delivery fee and price

Delivery fee is a flat binary rule in `order-service`, not a per-city lookup table: `Бишкек` (case-insensitive, whitespace-trimmed) costs `app.delivery.bishkek-fee`, every other region costs `app.delivery.default-fee`. This used to be a `Map<String, BigDecimal>` keyed by city name, but a Cyrillic YAML map key (`бишкек: 250`) silently broke Spring's relaxed YAML-to-Map binding — the value flattened onto `app.delivery.fees` itself instead of a nested entry, and the app failed to boot. Plain scalar properties don't have that failure mode. The frontend's city dropdown (`DELIVERY_CITIES` in `utils/deliveryFee.ts`) mirrors this exact rule for a live cart preview only; the checkout response is what's actually charged.

The admin enters the final customer price per variant directly (`priceOverride`, mandatory — `VariantRequest` rejects a missing or non-positive value); there is no markup or rounding. Every `ProductDto`/`VariantDto` still carries a `displayPrice`, but `PriceCalculator` now just passes the variant's own price through (falling back to `Product.basePrice`, i.e. the cheapest variant, when a variant has none), so `displayPrice === priceOverride` in practice. Every customer-facing surface (catalog, product page, cart) reads `displayPrice`.

`Product.basePrice`/`Product.imageUrl` are no longer admin-entered — `ProductRequest` doesn't carry them at all. `CatalogService` derives `basePrice` as the cheapest variant's `priceOverride` and `imageUrl` as the first image found across variants (`null` if none), on every create/update. A product must have at least one variant — `createProduct`/`updateProduct` both 400 on an empty variant list, so there's no more auto-generated `DEFAULT-*` placeholder variant, and a product without a variant can't exist (and so can't have a price or an image, both of which live only on the variant).

## Auth

`catalog-service` write endpoints (`POST`/`PUT`/`DELETE` under `/api/catalog/**`) require a JWT with `ROLE_ADMIN`, issued by `POST /api/auth/login`. GETs stay public. One hardcoded admin user, bcrypt hash in `application.yml` for local dev, overridden by `APP_SECURITY_ADMIN_PASSWORD_HASH` in prod. Login is rate-limited in-memory (resets on restart — fine for one instance, won't hold once there's more than one): 5 attempts/min per client IP, plus a global 20 attempts/min backstop across all clients. The per-IP key is `getRemoteAddr()` under `forward-headers-strategy=framework`, i.e. it comes from `X-Forwarded-For` — which Caddy overwrites with the real TCP peer (`header_up X-Forwarded-For {http.request.remote.host}`, and it strips inbound `Forwarded`/`X-Forwarded-Host`). Since Caddy is the only ingress, a client can't rotate that header to get a fresh bucket per request; the global cap is what bites if that ever stops being true.

`order-service` doesn't issue tokens itself — `GET /api/orders` validates the same JWT via its own copy of the JWT filter/security config, trusting whatever `catalog-service` signed. This only works because both services are given the identical `APP_JWT_SECRET`; rotate it in one place without the other and cross-service auth breaks. `POST /api/orders/checkout` stays public, same as before.

401 vs 403: 401 is no/invalid token, 403 is a valid token with the wrong role. Both come back through a custom `AuthenticationEntryPoint`/`AccessDeniedHandler` so they get the same JSON error shape as everything else instead of Spring Security's default empty body.

## Media upload

`POST /api/media/upload` (admin-only) pushes the file to S3-compatible storage and returns a public URL. `ProductForm` only offers per-variant upload slots now (`variant.image_urls`) — there's no product-level image field in the admin UI or in `ProductRequest` anymore, so every URL this endpoint returns ends up on a variant. Locally that's MinIO; point the `S3_*` env vars at Cloudflare R2 and it's the same code path. Bucket is created with a public-read policy on `catalog-service` startup if it doesn't exist. `S3StorageService.uploadFile` decodes the upload with `ImageIO.read` and, if both dimensions exceed 1600px, resizes it to fit within a 1600×1600 box (`Thumbnailator`, aspect-ratio preserved, no upscaling) and re-encodes as JPEG at quality 0.82, changing the key's extension to `.jpg` and `Content-Type` to `image/jpeg`; anything that doesn't decode as a raster image (non-image files, or formats `ImageIO` doesn't support like WebP/HEIC) or is already small enough uploads unchanged, exactly as before. The whole file is buffered into memory to do this — fine for admin-uploaded product photos, not designed for arbitrary uploads at scale.

## Catalog search/filter

`GET /api/catalog/products` takes `search`, `category`, `color`, `size`, `volumeMin`, `volumeMax` query params, plus `page`/`pageSize` (defaulting to `0`/`1000`). `search` is an `ILIKE` on product name; `category` is an exact case-insensitive match on `product.category`; `color`/`size` are exact case-insensitive matches against the `variant.attributes` JSONB column (`attributes ->> 'color'`, etc.), ANDed together. `volumeMin`/`volumeMax` are a real numeric range — `(attributes ->> 'volume')::numeric BETWEEN ...` — guarded by a regex check (`attributes ->> 'volume' ~ '^[0-9]+(\.[0-9]+)?$'`) before the cast, so a variant whose `volume` isn't a plain number (legacy or malformed data) is excluded from range results instead of throwing and failing the whole query. The frontend's color/size filter pills are a hardcoded list of common values, not pulled from actual data. The category dropdown is the exception: `GET /api/catalog/categories` takes the same `search`/`color`/`size`/`volumeMin`/`volumeMax` params (no `category`, no pagination) and returns `SELECT DISTINCT p.category ...` scoped by those same filters — a second native `@Query` on `ProductRepository` alongside `search`/`countQuery`, with a duplicated WHERE clause (native SQL doesn't compose the way a JPA Specification would; this mirrors `search`'s own `countQuery` already duplicating its WHERE clause in the same file). `CatalogPage` gets its options from `useCategories({ search, color, size, volumeMin, volumeMax })` — a small dedicated hook, not a second full product fetch — so selecting "Розовый" narrows the category list to categories that actually contain pink products, and the dropdown only renders once that list is non-empty.

The response is `ProductPageResponse { items, totalCount, page, pageSize }`, not a bare array — `ProductRepository.search` is a native query with a matching `countQuery` (Spring Data can't derive a count from an arbitrary native SQL query on its own) and returns `Page<Product>`. Pagination itself is mobile-only, since the compact 2/3-column grid densities are a mobile-only concept (`sm:`+ always shows the full 2/3/4-column desktop grid) — `CatalogPage` reads `useIsMobileViewport()` (a `window.matchMedia('(max-width: 639px)')` listener, matching Tailwind's `sm` breakpoint) and only passes `{ page, pageSize: 12 }` to the main `useCatalog` call when that's true; on desktop it requests `{ page: 0, pageSize: 1000 }` instead, i.e. still fetches everything in one page like before. 12 is the LCM of 1/2/3, so a mobile page always fills whole rows at any of the three mobile column counts with no ragged partial row. `Pagination` renders numbered page buttons (windowed with an ellipsis once there are many pages), only appears once `totalCount` exceeds one page, and is only rendered at all on mobile. Changing any filter resets to page 0 via a `useEffect` keyed on the filter values; callers that want "everything" regardless of viewport (the category-options fetch, and `AdminDashboard`'s unfiltered `useCatalog()`) simply omit the pagination argument and get the 1000-item default.

`ATTRIBUTE_KEY_OPTIONS`/`ATTRIBUTE_VALUE_OPTIONS` in `frontend/src/utils/attributeOptions.ts` are the shared source of truth for `color`/`size`: `ProductForm`'s value picker and `FilterBar`'s filter pills draw from the exact same Russian value lists, so a value an admin picks is guaranteed filterable — the label *is* the stored value. `SINGLE_SELECT_FILTERS` (same file) turns those two into one `{ key, label, options }[]` config that both `FilterBar` (desktop dropdowns) and `FilterSheet` (mobile accordion) `.map()` over instead of hand-writing a `color` block and a `size` block each — `category` (options loaded from real product data) and `volume` (a от/до range, not a single-select) stay as their own explicit blocks in both components since they're structurally different, not just differently labeled. `volume` is the exception to "dropdown-only" — it's a plain number (мл) entered in a number input, matched by `VolumeRangeFilter`'s от/до range instead of an exact-match pill. Beyond color/size/volume, `ProductForm` also lets an admin add a fully custom attribute (a free-typed key and value, via "+ Другой атрибут") for descriptive tags that aren't meant to be filterable — a variant loaded with a key outside `color`/`size`/`volume` opens straight into that free-text mode. Every variant attribute (preset or custom) renders as a small tag — on `ProductCard` for its primary variant, and on `ProductPage` for whichever variant is currently selected — formatted through `formatAttributeValue` (which appends "мл" for `volume`, since it's stored as a bare number). The product-page variant *selector* itself shows `variant.sku` (the admin-entered name, e.g. "Розовый") as each button's label, not attributes — attributes are what's filterable and what shows as tags, the name is what a customer picks between. A variant whose `sku` is still an old auto-generated `DEFAULT-*` code (pre-dating variants becoming mandatory) falls back to its attribute values, or `Вариант N`, as the button label instead of showing the raw code.

## Mobile catalog grid density

Below Tailwind's `sm` breakpoint, `ProductGrid` renders 1/2/3 columns based on a customer-controlled `mobileColumns` value (`MobileColumnsToggle`, shown mobile-only) instead of a fixed column count — `sm:`/`lg:`/`xl:` still force 2/3/4 columns as before regardless of that choice, since the toggle only exists to solve cramped mobile widths. The choice persists in `localStorage` (`catalog-mobile-columns`, defaulting to 2) so it survives a reload. `ProductCard` reads the same `mobileColumns` value and progressively simplifies via `max-sm:*` utility classes (real CSS media queries, not JS conditional-rendering, so nothing here is affected at `sm`+ regardless of the mobile choice): at 2 columns the description, category, attribute tags, and variant-count badge hide, the title shrinks to a single truncated (`…`) line, the price shrinks a step, and the quantity stepper + full-width "В корзину" row is replaced by a separate full-width icon-only add-to-cart button below the price; at 3 columns the product name additionally hides, leaving image/price/cart-icon only. The compact and full add-to-cart controls both exist in the DOM at once and are toggled by the same `max-sm:hidden`/`max-sm:flex` media-query pair — there's no separate "compact" state, just CSS visibility keyed off `mobileColumns`.

## Product card navigation transition

Opening a product card and going back to the catalog plays a retro Win9x-style "growbox" wireframe: a bordered rectangle that expands from the clicked card's rect to fill the content area, or collapses back down onto it. State lives in `useCardTransitionStore` (zustand): `originRect` (the clicked card's `getBoundingClientRect()`, captured via `onClickCapture` on `ProductCard`'s root, since the card has multiple inner `<Link>`s) and `phase` (`'expand' | 'collapse' | null`). `WireframeTransition` is mounted once at the top of `App.tsx`, outside `<Routes>`, so it survives route changes instead of remounting per page; it snaps to the "from" rect with `transition: none`, then on the next two animation frames applies the "to" rect with a `linear` CSS transition (period-accurate — no easing, no fade, the box just disappears once the resize finishes). Clearing is a `setTimeout` matched to the transition duration (plus a small buffer), not `transitionend` — relying on a specific CSS property firing `transitionend` proved fragile for very different from/to aspect ratios and could leave the border stuck on screen. The target/origin for "fullscreen" isn't the raw viewport — `getContentBounds()` measures the sticky header's bottom edge and the mobile tab bar's top edge at animation time, so the wireframe never draws over the always-visible nav chrome. `ProductPage`'s "← Каталог" link triggers `collapse` reusing the same stored `originRect`, so it shrinks back onto the same card position; a direct URL visit (no prior card click, `originRect` still null) plays no animation. Separately, `ProductGrid`'s wrapper is keyed on `mobileColumns` so switching column density remounts it with a quick `animate-grid-density-pop` scale/fade-in keyframe instead of an instant reflow.

## Mobile filter sheet

Below `sm`, the individual `FilterDropdown`/`VolumeRangeFilter` pills in `FilterBar` are replaced by a single `FilterSheet` trigger ("Фильтры", with an active-filter count badge) that opens a bottom sheet covering 70% of the viewport height (`h-[70dvh]`). `FilterBar` itself is gated `hidden sm:flex` so desktop is untouched. The sheet slides up with `framer-motion` (`y: '100%'` → `0`, tween/easeOut, same pattern as `CartDrawer`) rather than the product-card wireframe transition — the growbox effect didn't read well for such an extreme aspect-ratio jump (small pill button to a near-full-width sheet), so this is a deliberately different, more conventional motion. Each filter group (Категория/Цвет/Размер/Объём) renders as its own collapsed accordion row inside the sheet — tap a header to expand its option chips (or the от/до inputs for Объём) — mirroring the desktop dropdown affordance without the aspect-ratio problem of full-page dropdown popovers. Selections are draft-only until "Показать товары" commits them all at once via the same `onXChange` props `FilterBar` uses; closing any other way (backdrop, "Закрыть") discards the draft. A tiny `useFilterSheetStore` (`isOpen` boolean) is read by `NavigationBar` and OR'd into its existing scroll-based `hidden` state, so both the sticky header and the mobile tab bar slide away while the sheet is open, the same way they already do on scroll.

## Error shape

Both backend services return `{status, error, message, path, timestamp, fieldErrors?}` from a `@RestControllerAdvice`, for validation errors, 404/409s, and unhandled exceptions (500, no internal details leaked). The frontend shows the server's `message` on toast where there is one, a generic fallback otherwise, and a "session expired" toast on 401. Canceled requests (React StrictMode's double-effect abort/remount) are explicitly excluded from the toast — they used to show a false-positive error on every page load.

## Prod compose hardening

`docker-compose.prod.yml` runs the full stack in containers with a Caddy reverse proxy in front (`Caddyfile`) — Caddy is the only container with a public port (80/443), TLS via Let's Encrypt for a real `DOMAIN` or a self-signed cert for `localhost`. `api-gateway`, `catalog-service` and `order-service` publish no host ports at all. `postgres-db` and the RabbitMQ broker port (5672) publish nothing — the app containers reach them by service name over the `adikabuyer-network` bridge. The RabbitMQ management UI (15672) and MinIO (9000/9001) are bound to `127.0.0.1` only, so they are reachable for debugging via an SSH tunnel but never from the internet. All infra passwords and the JWT secret are required env vars (`:?` in compose) — missing any of them refuses to start rather than falling back to a default. Both `catalog-service` and `order-service` run with `SPRING_PROFILES_ACTIVE=prod`; the `application-prod.yml` profile turns `APP_JWT_SECRET` / `APP_SECURITY_ADMIN_PASSWORD_HASH` into hard `:?` placeholders, so a missing secret fails at Spring context startup with a clear error instead of silently booting on the insecure dev fallback baked into `application.yml`. Every container has a `mem_limit` above its JVM `-Xmx` and a `HEALTHCHECK`.

Live at `https://adikabuyer.kg` on a Hetzner VPS, deployed via `.github/workflows/deploy.yml` on every push to `main`.

## Framework baseline

All three services are on **Spring Boot 4.1** / Java 21; `api-gateway` adds **Spring Cloud 2025.1** (`spring-cloud-starter-gateway-server-webflux`). Things that bit during the 3.3 → 4.1 jump, for future reference:

- Test slices split into their own starters — `@WebMvcTest` needs `spring-boot-starter-webmvc-test`, and `@MockBean`/`@SpyBean` are gone (use `@MockitoBean`/`@MockitoSpyBean` from `org.springframework.test.context.bean.override.mockito`).
- Auto-config packages moved: `org.springframework.boot.autoconfigure.security.servlet.*` → `org.springframework.boot.security.autoconfigure.*` (and similarly per module).
- Jackson 3: databind is `tools.jackson.databind.*` (annotations stay `com.fasterxml.jackson.annotation.*`); `java.time` support is built in, no `JavaTimeModule`.
- Spring Cloud Gateway reactive config moved under `spring.cloud.gateway.server.webflux.{routes,globalcors}`.
- `RestClient.Builder` is not auto-configured for a plain Spring MVC app; `TelegramConfig` calls `RestClient.builder()` directly.
- **Flyway** auto-configuration moved to its own module — `org.flywaydb:flyway-core` on the classpath is no longer enough, you need `org.springframework.boot:spring-boot-starter-flyway` (plus `flyway-database-postgresql`). Without it Flyway silently never runs and Hibernate `ddl-auto: validate` fails on a fresh database.
- Spring AMQP 4.1 defaults to a **Jackson 2** message converter whose ObjectMapper has no `java.time` handler — `new Jackson2JsonMessageConverter()` throws on an `Instant` field. Both services use `new JacksonJsonMessageConverter()` (Jackson 3) instead.
- `@Valid` directly on a `List<X>` is deprecated (Hibernate Validator 9, `HV000271`) — moved to `List<@Valid X>`.
- `api-gateway` gained a `contextLoads` `@SpringBootTest`; the whole stack (`docker-compose.prod.yml`, fresh volumes) was smoke-tested — Flyway migrations, product CRUD, media upload, checkout, and RabbitMQ inventory deduction all verified end-to-end through Caddy.

order-service's `RabbitMQConfig` no longer declares `order.queue` / its binding — it's a producer, the queue (with its dead-letter args) is catalog-service's. Declaring it from both sides with different arguments caused `PRECONDITION_FAILED` on a fresh broker.
